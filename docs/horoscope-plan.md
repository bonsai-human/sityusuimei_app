# ホロスコープ対応の計画

四柱推命の命式に加えて、西洋占星術のネイタルチャート（出生図）も同じアプリで組めるようにする。

いま入力している「いつ・どこで生まれたか」は両方で共通なので、入力をもう一度させることはしない。
一度書いたら、命式とホロスコープの両方が出る。プロンプトも、片方だけ／両方まとめての
どちらでも書き出せるようにする。

すべてブラウザの中で完結させる方針は変えない。外部の計算 API は使わない。

---

## 0. 先に決めておくこと

実装より前に決着が要る点を先に並べる。ここがぶれると後から作り直しになる。

### 0-1. 出生地に緯度が要る（既存データの移行が発生する）

`BirthPlace` はいま経度と標準時オフセットしか持っていない。四柱推命の真太陽時補正には
それで足りるが、アセンダントとハウスは緯度が無いと出せない。

```ts
export interface BirthPlace {
  label: string;
  longitude: number;
  latitude: number;        // 追加。北緯を正とする
  tzOffsetMinutes: number;
}
```

移行が要る場所は 3 つ。

| 置き場 | いまの状態 | どうするか |
| --- | --- | --- |
| `data/cities.ts` | 全 29 都市に緯度なし | 表に緯度を書き足す（座標は公的な資料から） |
| `store/appStore.ts`（localStorage） | `persist` version 2 | version 3 の `migrate` で、都市名が一覧にあれば緯度を補う |
| `db/database.ts`（IndexedDB） | 保存済み命式の `input.place` | Dexie version 3 の `upgrade` で同じく都市名から補う |

一覧に無い土地（自分で経度を打った場合）は緯度が分からないので補えない。その場合は
ホロスコープの画面で「緯度が未入力です」と出して入力を促す。四柱推命の側は緯度が無くても
これまで通り動くので、既存の保存データが壊れることはない。

### 0-2. 時刻の扱いが四柱推命と違う

ここが一番の落とし穴。**ホロスコープに真太陽時の補正を掛けてはいけない。**

- 四柱推命 … 日柱・時柱はその土地の太陽の位置で決まるので、経度補正と均時差を掛けた時刻を使う
- ホロスコープ … 天体の位置は世界時（UT）の関数。時計の時刻から標準時オフセットを引くだけでよい。
  経度は「その瞬間の空をどの向きから見上げるか」としてアセンダント側で効くので、時刻に足すと二重に効く

つまり `UT = 時計の時刻 − サマータイム分 − tzOffsetMinutes` で、`solarTime.ts` の補正は通さない。
`ChartOptions.trueSolarTime` / `equationOfTime` はホロスコープには一切効かない、と画面にも書く。

### 0-3. 出生時刻が不明のとき

四柱推命では時柱を落とすだけで残りは組めるが、ホロスコープでは影響が大きい。

- アセンダント・MC・ハウスは**出さない**（1 時間で 15 度、つまり半分のハウスが入れ替わる）
- 月は 1 日で 12〜15 度動くので、度数ではなく**その日の範囲**として示す（星座をまたぐ場合はその旨も）
- 太陽から冥王星までのサイン（星座）は 1 日ではほぼ動かないので、そのまま出してよい

「出せないものは出さない、出すなら根拠と誤差を添える」という既存の作法をそのまま踏襲する。

### 0-4. 天体暦のライブラリ

[astronomy-engine](https://github.com/cosinekitty/astronomy)（MIT、2.1.19）を使う。

- 太陽・月・水星〜冥王星の見かけの地心位置が出る（`GeoVector` + `Ecliptic` で、その日の
  真の黄道座標＝トロピカルの黄経がそのまま得られる）
- グリニッジ視恒星時（`SiderealTime`）が出るので、アセンダントと MC を自前で組める
- 月の交点（`SearchMoonNode`）と月の遠地点（`SearchLunarApsis`）も出る
- 依存ゼロ、ブラウザで動く、TypeScript の型つき。ESM 版で 420KB（minify 後 135KB、gzip でおよそ 45KB）
- 冥王星の対応範囲は 1700〜2200 年。出生図には十分だが、範囲外は明示的にエラーにする

代わりに検討したもの:

| 候補 | 見送った理由 |
| --- | --- |
| swisseph 系（WASM） | 精度は最高だが GPL。このアプリの配布形態と噛み合わない |
| astronomia | 汎用の天文計算。必要な天体を自分で組み上げる手間が astronomy-engine より大きい |
| circular-natal-horoscope-js | 占星術専用で楽だが、内部の精度と誤差の出どころが追いにくい |

**キロン・小惑星は入らない**（astronomy-engine が持っていない）。軌道要素を自前で持てば出せるが、
初回の範囲からは外す。リリスは平均値（月の平均遠地点）を式で出す。

バンドルは、ホロスコープの画面を `React.lazy` で切り出して astronomy-engine をそこからだけ
参照させ、四柱推命しか使わない人が読み込まずに済むようにする。計算層そのものは同期のまま
（テストからは普通に import できる）。

### 0-5. 良し悪しを点数にしない方針は変えない

四柱推命の合・沖を点数にしなかったのと同じ理由で、アスペクトも「調和／緊張」の色分けと
オーブ・接近／分離の事実だけを出す。「相性 80 点」は出さない。

## フェーズ 4 — 計算層

`src/core/horoscope/` を新しく作る。既存の `src/core/*.ts` には手を入れない
（`types.ts` の `BirthPlace` に緯度を足すのを除く）。

```
src/core/horoscope/
  constants.ts   サイン・天体・ハウス・アスペクトの表と和名
  bodies.ts      天体の黄経・黄緯・日々の移動量・逆行の判定
  angles.ts      恒星時 → ASC / MC / Vertex
  houses.ts      ハウス分割（プラシーダス／ホールサイン／イコール／ソーラーサイン）
  aspects.ts     アスペクトの走査、オーブ、接近／分離
  chart.ts       入力 → ネイタルチャート（buildHoroscope）
  types.ts       Horoscope, Placement, House, Aspect ...
```

### 4-1. 天体（bodies.ts）

10 天体（太陽・月・水星・金星・火星・木星・土星・天王星・海王星・冥王星）と、
ドラゴンヘッド（平均／真の交点を切り替え）、リリス（平均遠地点）。

- 逆行は、前後半日の黄経の差から日々の移動量を出して符号で判定する
- サイン・度数・分は黄経から機械的に導く。度数は 0.01 度まで出す

### 4-2. 感受点（angles.ts）

```
RAMC   = GAST(度) + 経度
MC     = atan2(sin(RAMC), cos(RAMC)·cos ε)
ASC    = atan2(cos(RAMC), −(sin(RAMC)·cos ε + tan(緯度)·sin ε))
```

象限の取り違えが定番の事故なので、南半球（緯度が負）と MC が黄経 0 度をまたぐ場合を
テストで固定する。

### 4-3. ハウス（houses.ts）

| 方式 | 位置づけ |
| --- | --- |
| プラシーダス | 既定。日本の書籍・アプリで最も見かける |
| ホールサイン | ASC のあるサインを丸ごと 1 室にする。古典寄り |
| イコール | ASC から 30 度ずつ |
| ソーラーサイン | 出生時刻が不明なときだけ。太陽のサインを 1 室に置く |

プラシーダスは半弧を三分する反復計算で 11・12・2・3 室を出し、残りは対向で埋める。
緯度が高い（およそ 66.5 度以上）と解が出ないので、そのときはホールサインに落として
「この緯度ではプラシーダスが定義できないので◯◯で表示している」と画面に断る。
流派が分かれるところを設定で選ばせ、既定の根拠を画面に出す作法は四柱推命と揃える。

### 4-4. アスペクト（aspects.ts）

- メジャー: 合 0 / 衝 180 / 三分 120 / 四分 90 / 六分 60
- マイナー（既定オフ）: 150 / 30 / 45 / 135
- オーブは表で持ち、太陽・月は広めに取る（既定: メジャー 8 度、太陽・月が絡めば 10 度、
  六分 6 度、マイナー 2 度）。設定から動かせる
- 移動量の差から**接近中か分離中か**を出す（四柱推命の側に無い、占星術ならではの情報）
- 天体どうしだけでなく、ASC / MC に掛かるものも同じ関数で走査する

`relations.ts` の `pairRelations` が「1 つの命式の中でも、2 つの命式のあいだでも、
大運が命式に掛ける関係でも同じ判定を使う」構造になっているのと同じで、
`pairAspects(群 A, 群 B, オーブ表)` の一本に寄せる。ネイタル・トランジット・シナストリーが
これ一つで足りる。

### 4-5. 全体の傾き（chart.ts に同梱）

- エレメント（火・地・風・水）とクオリティ（活動・不動・柔軟）の分布。四柱推命の五行バランスと同じ見せ方
- 昼の図か夜の図か（太陽が地平線の上か下か）
- ASC のサインの支配星が、どのサイン・どのハウスに居るか
- 3 天体以上が同じサイン／ハウスに固まっていれば、その旨
- 半球（東西・南北）の偏り

### 4-6. テスト

`src/core/horoscope/__tests__/` に、四柱推命と同じくゴールデンケースを置く。

- 外部の実装（Swiss Ephemeris ベースの公開サイト）と突き合わせた出生図を 5 例
  （東京・南半球・西経・高緯度・時刻不明）
- 許容差は天体の黄経で ±0.02 度、ASC / MC で ±0.1 度。1 か所でもずれたら落とす
- 境界: 逆行の留の前後、月が日付をまたいでサインを移る日、サマータイム中、
  日付変更線の東西、プラシーダスが破綻する緯度

見積もり: 計算層 900〜1100 行 + テスト 400 行。

## フェーズ 5 — 画面

### 5-1. 占術の切り替え

いまのタブ（入力／命式／プロンプト／保存済み／比較／人生ログ）は「何をするか」で切ってある。
ここに「ホロスコープ」を 1 タブ足すと、プロンプト・比較・人生ログの側が四柱推命専用のまま
取り残される。

そこで、ヘッダに **占術の切り替え（四柱推命／ホロスコープ／両方）** を置き、
既存のタブはその選択に従って中身が変わる形にする。入力は共通なので、入力タブは
選択に関係なく 1 つのまま（緯度の欄だけホロスコープが要るときに現れる）。

「両方」のときは、命式の下にホロスコープを縦に並べる。

### 5-2. 出生図（円形チャート）

SVG で自前で描く。外部のチャート描画ライブラリは入れない（比較画面の関係線を
`RelationLines.tsx` で自前で引いたのと同じ方針）。

- 外周にサイン、内側にハウス、天体をその黄経の位置に。近すぎる天体は重ならないよう押し広げる
- 中央にアスペクトの線。調和と緊張で色を分ける（既存の合＝結びつき／沖＝揺さぶりの色分けに揃える）
- 天体・サインの記号は文字（♈ ☉ など）に頼るとフォント次第で崩れるので、SVG のパスで持つ
- 濃淡どちらのテーマでも読めるよう、色は既存の CSS 変数から取る

### 5-3. 表の側

円だけでは読みにくいので、四柱推命の `PillarCard` に相当する表も出す。

- 天体表: 天体／サイン／度数／ハウス／逆行／支配するハウス
- ハウス表: カスプのサインと度数
- アスペクト表: 相手・種類・オーブ・接近／分離
- エレメントとクオリティの分布（`ElementBalance` の見せ方を流用）

見積もり: 6 コンポーネント、800〜1000 行。

## フェーズ 6 — プロンプト

`core/horoscope/prompt.ts` を足し、既存の `PromptConfig` に占術の次元を持たせる。

- テンプレート: 総合／今年（トランジット）／仕事・適職／恋愛・結婚／体質／自由記述、
  そして **四柱推命とホロスコープを併記して読ませる統合テンプレート**
- 統合テンプレートの依頼文は「両方で同じことを言っている点と、食い違う点を分けて述べてください」
  という形にする。二つの体系を機械的に足し算させても意味が無い
- 含める項目の選択（ハウス／アスペクト／マイナーアスペクト／ドラゴンヘッド／トランジット……）
- Markdown / JSON / 圧縮の 3 形式は既存の枠をそのまま使う
- 度数は「牡羊座 12°34′（第 3 室）」のように、サインとハウスを必ず添える形で書き出す
  （数字だけ渡すと読み違えられる）

`promptConfig` の形が変わるので、`persist` の migrate をもう一段足す。

見積もり: 500〜600 行。

## フェーズ 7 — トランジットとプログレス（人生ログとの接続）

四柱推命の大運・流年に当たるものを用意し、人生ログにつなぐ。

- **トランジット** — 指定日の天体が、出生図のどこに掛かっているか
- **二次進行**（1 日 = 1 年）— 進行の月・太陽のサイン移動、進行の新月／満月
- **ソーラーリターン** — 太陽が出生図と同じ黄経に戻る瞬間の図（＝その 1 年の図）

人生ログの各行に、いまの「大運・流年」と並べて「そのときのトランジット」を出せるようにする。
**同じ出来事を二つの体系から見る**形になり、答え合わせとしての価値がいちばん上がるところ。
「当てにいくためではなく、読み方を確かめるため」という既存の断りもそのまま効く。

見積もり: 400〜500 行 + 画面の手当て。

## フェーズ 8 — シナストリー（比較画面）

比較画面の柱どうしの線を、そのまま天体どうしの線に置き換える。

- 二重円（内側に本人、外側に相手）と、二人のあいだのアスペクト表
- 相手の天体が本人のどのハウスに落ちるか（占星術ではここが要）
- 読み所は、太陽・月・ASC・金星・火星に掛かるものだけを言葉で添える
- 点数は出さない

`pairAspects` が既にあるので、計算はほぼ足すものが無い。見積もり: 300 行前後。

## 進捗と、計画からの変更点

### 済み

- **出生地の緯度**（コミット「出生地に緯度を持たせる」）— 3 経路の移行込み
- **フェーズ 4: 計算層**（`src/core/horoscope/`）— 天体・感受点・ハウス 4 方式・
  アスペクト・全体の傾き
- **フェーズ 5: 画面** — 占術の切り替え、出生図の円、天体・ハウス・アスペクトの表、読み方の設定
- **フェーズ 6: プロンプト** — ホロスコープの 6 テンプレートと、四柱推命と併記する統合テンプレート

テストは 223 件。

### 変更点 1 — 検算の当てを、外部の天体暦から幾何に変えた

計画では「外部の実装（Swiss Ephemeris ベースの公開サイト）と突き合わせる」としていたが、
この開発環境からは外部への接続が塞がれていて（JPL Horizons も含めて）取りに行けなかった。

代わりに、**独立に求まる量との突き合わせ**で固めている。閉じた式で出した値を同じ式で
検算しても意味が無いので、検算には astronomy-engine の座標変換だけを使う。

| 確かめるもの | 当て方 |
| --- | --- |
| アセンダント | その黄経の点を地平座標に直し、高度が 0 で方位が東半分（0〜180 度）にあること |
| MC | 時角が 0 で、IC より高い位置にあること |
| バーテックス | 方位がちょうど 270 度（真西を通る大円の上）にあること |
| プラシーダス | 各カスプの時角が、その点の半弧をちょうど 3 等分していること |
| 高緯度 | プラシーダスが解けず、ホールサインに落ちて注記が付くこと |
| 太陽の黄経 | 春分の瞬間に 0 度、夏至の瞬間に 90 度になること（分点の時刻は別経路で求まる） |
| 太陽と月 | 朔の瞬間に重なること（光行差のぶん 20 秒角ずれることまで固定） |
| 逆行 | 速度の符号が、前後 2 日の黄経の増減と一致すること |
| 世界時への変換 | 正午生まれの太陽の時角が、経度差と均時差の合計に一致すること |

最後の 1 つが時刻まわりの要で、四柱推命側の `solarTime.ts`（NOAA の近似式）を当てにしている。
標準時のオフセットを取り違えれば 15 度ずれるので、そこで落ちる。

**外部との突き合わせ（済み・決着）**: 1990年1月1日 12:00 東京の図を、外部の実装 2 つと並べてもらった。

**2 つ目の実装とは、アセンダント・MC ともに完全一致した**（牡羊座 23°43′／山羊座 14°04′）。
1 つ目との差は下記のとおり、相手側が恒星時にして一定 26 秒ぶん遅れているためと判断している。

以下は 1 つ目の実装との突き合わせの記録。

- 太陽〜冥王星は一致。差は 0.01 度程度で、これは度分表示を小数に直すときの丸め幅
  （1 分 = 0.0167 度）に収まる
- アセンダントと MC はこちらが 9 分・6 分だけ先行していた

感受点の差は、**地方恒星時にして 26 秒ぶんの差**だった。アセンダントと MC はどちらも
地方恒星時を通して効くので、時刻や経度がずれたときに動く量の比は一定になる。
この図では 1 分あたり ASC 0.375 度・MC 0.233 度（比 1.612）で、報告された差の比は 1.613。
つまり片方だけがずれているのではなく、恒星時が一様にずれている形。

出どころを切り分けた結果、**こちらの値が正しい**と判断している。2 つ目の実装との一致が
それを裏づけた。

- 相手の資料が使っていた座標（東経 139 度 46 分・北緯 35 度 40 分）で組み直しても、
  こちらの値は変わらない（このアプリの東京は 139.7671/35.6812 で、ほぼ同じ地点）。
  緯度は MC に効かないので、緯度の違いでもない
- こちらの視恒星時は、IAU の平均恒星時の多項式と 0.73 秒（＝分点差そのもの）で一致する
- こちらのアセンダントは、式をいっさい使わず二分法で求めた「地平線に乗る黄道上の点」と
  **0.00 秒角**で一致する（この数値解は astronomy-engine の座標変換だけを通り、
  こちらの恒星時にもアセンダントの式にも依存しない）

4 つの時刻（9時・12時・15時・21時）で確かめたところ、ずれは時刻に比例せず一定だった。
恒星時を 0.109 度ずらすだけで、相手の 8 つの値すべてが 0.006 度以内で再現できる。
つまり相手は、表示している東経 139 度 46 分より 6.5 分だけ西の子午線で計算していることになる。

この 2 つは常設のテストにした。画面にも座標と「時刻 1 分あたりどれだけ動くか」を
出すようにしたので、他の資料と並べたときに切り分けられる。

### 変更点 2 — バーテックスの式

南半球で「余緯度を 90 −|緯度| にして反対側を取る」としていたが、これは誤りだった。
正接の周期が 180 度なので、**南半球でも 90 −緯度（90 度を超える値）をそのまま通せばよい**。
方位 270 度の検算で発覚し、直してある。

### 変更点 3 — ハウスの方式と天体の設定の置き場

計画では触れていなかったが、ハウスの方式・ドラゴンヘッドの取り方・オーブは
`BirthInput` ではなく**アプリ側の設定**（store）に置くことにした。四柱推命の流派の設定は
その人の命式の性質として `BirthInput` に入っているが、ハウスの方式は読み手の好みであって
その人に属する情報ではないため。保存済みデータの移行も要らなくなる。

## 気をつける点

- **緯度の移行** — 保存済みの命式が壊れないこと。四柱推命の側は緯度が無くても従来通り動く
- **`sect` という語の衝突** — `ChartOptions.sect` は既に「大運の起算流派」の意味で使っている。
  占星術の昼夜（sect）は別の名前（`dayChart`）にする
- **バンドルの肥大** — 動的 import で切り分け、四柱推命だけの利用者に読み込ませない
- **アプリの名前** — 「命式ノート」は四柱推命の語。ホロスコープが入ると看板と中身がずれるので、
  フェーズ 5 の時点で名前と説明文をどうするか決める
- **精度の断り書き** — 天体の位置には誤差があること、ハウスの流派で結果が変わることを、
  真太陽時の説明と同じ調子で画面と README に書く
